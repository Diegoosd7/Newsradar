# ADR-0006: Elección de ORM para el acceso a la base de datos

> ESTADO: ACEPTADO  
> FECHA: 2026-03-11

## Contexto
Necesitamos una capa de abstracción para acceder a la base de datos desde 
los endpoints de la API REST. Esta capa debe permitir hacer queries de forma 
agnóstica al motor de base de datos, facilitando la futura migración de SQLite 
a PostgreSQL, y debe integrarse bien con FastAPI y Python.

## Alternativas consideradas
- **SQLAlchemy** — ORM estándar de Python, muy completo, compatible con 
  múltiples motores de base de datos y con FastAPI
- **Tortoise ORM** — diseñado específicamente para uso asíncrono con FastAPI, 
  pero con ecosistema más pequeño y menos documentación
- **Peewee** — ligero y sencillo pero con menos funcionalidades y peor 
  integración con FastAPI

## Decisión
Usaremos SQLAlchemy como ORM para el acceso a la base de datos.

## Consecuencias
- SQLAlchemy es el ORM más utilizado en el ecosistema Python, con amplia 
  documentación y comunidad activa.
- Al ser agnóstico al motor de base de datos, facilitará la migración de 
  SQLite a PostgreSQL en producción sin cambiar la lógica de acceso a datos.
- Se integra bien con FastAPI mediante sesiones de base de datos inyectadas 
  como dependencias en los endpoints.
- Como deuda técnica del Sprint 1, el patrón de acceso a datos entre ORM 
  y el repositorio (`dict_repository.py`) no está del todo consolidado y 
  deberá estandarizarse en el Sprint 2.
